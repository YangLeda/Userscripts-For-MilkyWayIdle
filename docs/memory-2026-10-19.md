# 2026-10-19 内存增长排查

玩家反馈：不操作，挂机时内存仍持续增加。以下为源码审查与 Ego Lite 隔离夹具结果，不是玩家真实角色的整页内存归因，也不是长时间进程 RSS 测量。没有改动游戏设置、角色状态或历史数据。

## 确认的问题与修复

### 资料面板的无限等待

`build-score.js` 的 `getInfoPanel` 在找不到人物资料面板时，每 500ms 新建一个 Promise，并以递归调用得到的下一个 Promise 作为 resolve 的值。前一个等待需要下一个完成，面板一直缺失时形成不断增长的 Promise 链。资料响应到了、但面板未挂载或已关闭，都可能启动这条路径；随后即使不再操作，等待仍不会结束。它不是每个全新游戏标签页都必然触发的路径。

`external-tools.js` 的导出按钮还为每次资料响应启动一个 200ms 的 interval，没有超时，找不到面板时保留闭包及相应人物资料。单个 interval 不会自己不断复制，但多次响应可能留下多个等待任务。

现在两者共用一个等待任务：单个 Promise，100ms 检查一次，最多等待 5 秒；面板出现则立即结束，缺失则返回 null。每次响应有请求序号，较新的评分／导出请求会取代旧请求；同一个面板只保留一个导出按钮。后续资料响应可以重新发起一次有限等待。

### 意见中心入口保留旧页头

旧 `ensureButton()` 每次发现入口已随页头移除，就创建新按钮并调用长期 feature scope 的 `event()`。scope 的清理闭包强引用旧按钮，按钮又通过 parentElement 留住已移除的页头。只要功能不关闭，旧树就可能累积。

现在复用同一个入口按钮，移到新页头；没有页头时先将按钮从旧父节点摘下，只绑定一次监听器。此问题主要与页头重建相关，不能用来解释完全没有页面变化时的增长。

同时移除初始化消息中对完整客户端和角色 payload 的控制台输出，避免控制台历史额外保留完整对象；未测量这部分在真实玩家环境中的独占占用。

## 原生 Chromium 验证

使用 ego-browser TaskSpace 182 的 about:blank 隔离页，测试后关闭。测试只加载相关仓库模块；计时器加速用于验证生命周期，不代表经历了相同的真实时间。每个测量点主动执行 `HeapProfiler.collectGarbage`，读取 `Runtime.getHeapUsage`；因此下列为 JS heap used，不是整个浏览器进程的内存。

原版等待函数直接取自修改前的 `build-score.js`。保持一个等待入口，面板始终缺失：

| 阶段                 | GC 后 JS heap used |
| -------------------- | -----------------: |
| 已执行 100 次回调    |      425,440 bytes |
| 再执行 20,000 次回调 |    1,310,740 bytes |
| 再执行 20,000 次回调 |    2,194,308 bytes |

每增加 20,000 次回调约留下 0.88 MB，且强制 GC 后仍增长。按旧 500ms 间隔，20,000 次约对应 2.78 小时，但这只是单个夹具的模拟周期，不能换算为玩家整页增长速度。

新等待模块在虚拟时间 5,000ms、50 次回调后返回 null，剩余定时器为 0。GC 后 JS heap 为 505,768 bytes；继续推进 40,000 个空闲周期，新增回调为 0，GC 后为 505,180 bytes。未见旧式持续增长。

页头夹具重复重建 20 次，每个页头包含 1,000 个文本 div；对旧页头只保存 WeakRef，实际长期保留 panel 及其 scope：

| 版本   | GC 后仍存活的旧页头 | CDP DOM nodes | embedder heap used |
| ------ | ------------------: | ------------: | -----------------: |
| 修改前 |             20 / 20 |        42,360 |    5,266,224 bytes |
| 修改后 |              0 / 20 |         2,140 |    1,531,760 bytes |

两者 JS heap 分别约 1.487 MB 和 1.481 MB，差异主要体现于 DOM／embedder heap，不能只看 JS heap 数字。

## 其他检查与范围

- DPS 常规图表为 150 个循环桶，完整图表最多 1,900 个桶，历史另有数量／字节限制；这些代码有上限，不能简单将缓存增长认定为无限泄漏。手动消息抓取是另一条可选路径，本次未开启、未修改。
- 资产历史同一天覆盖同一日期记录，不是每次快照都新增一个永久记录；短期内反复计算和序列化仍可能造成临时峰值。
- 共享存储保留删除标记与合并缓存是已知内存贡献项。本次未改动其删除语义和跨标签页合并，以免让旧标签页恢复已删除记录；尚未证明这是本次反馈的持续增长源。
- 未在真实持续战斗、多个其他脚本同时启用的玩家页面上做前后堆快照，不能宣称所有内存增长都已消失。若从未收到人物资料且没有页头重建，仍需真实页面的采样判断后续来源。

## 回归验证

覆盖同一页面 1,000 个等待调用只共享一个 Promise、5 秒后停止、新面板稍后出现可正常完成、超时后可重新等待、较新的导出请求取代旧请求，以及 30 次页头重建仍只绑定一次入口监听。保留既有人物评分、导出及意见中心行为测试；正式脚本不增加诊断面板、debug 产物或追踪接口。

`npm run build`、`npm run check` 和 `git diff --check` 通过，共 592 项测试。全量复核暂用 `node --test --test-concurrency=1`，完成后已恢复本地测试命令；既有强化计算性能断言保持原 50ms 阈值，单并发测得约 10ms。

## 继续排查：后台被动战斗

### 消息队列依赖后台定时器

确认另一条独立的积压路径：`src/core/messages.js` 将每条原始 WebSocket 消息放入模块级队列，每个 `setTimeout` 回调只取出 4 条。若后台定时器的处理速度低于消息到达速度，未处理的完整字符串就会持续保留；插件也会越来越落后于游戏状态。这是有条件的队列积压，并不要求人物资料或页头发生变化。尚未测得玩家浏览器实际采用的定时器限制，不能认定每位玩家都正在遭遇它。

改为微任务分批处理，原生消息读取先返回，再处理插件效果；后续批次不再等待定时器。保留 FIFO、每个事件只投递一次和逐条异常隔离，不丢弃战斗、库存或初始化消息。微任务之间允许其他已排入的微任务执行；它们不会像旧计时器那样让出完整的事件循环轮次，大型同步消息突发可能集中占用主线程。正常独立的 socket 事件之间仍有事件循环边界。未添加任何生产诊断接口或 debug 产物。

使用 ego-browser TaskSpace 183 的隔离 Chromium 页面，对照修改前 HEAD 的完整消息模块与修改后的模块。仅在夹具里暂停 `setTimeout`，持续生成独立消息并由原始 MessageEvent getter 入队；每个采样点强制 GC。消息体约 1–1.6 KB，消息消费者只统计顺序与数量：

| 已收到消息 | 修改前已处理 / GC 后 JS heap | 修改后已处理 / GC 后 JS heap |
| ---------- | ---------------------------- | ---------------------------- |
| 10,000     | 0 / 14,762,784 bytes         | 10,000 / 497,616 bytes       |
| 20,000     | 0 / 30,773,656 bytes         | 20,000 / 498,164 bytes       |
| 30,000     | 0 / 46,779,044 bytes         | 30,000 / 506,220 bytes       |

旧版始终只有一个等待执行的定时器，但队列持续增长；新版不依赖任何定时器，所有消息顺序正确。这是人为限制调度的压力复现，不是已确认的真实后台限速或现实增长率。

### 普通挂机、迷宫与公会试炼回放

在同一隔离浏览器页加载实际核心消息模块和完整 DPS 功能（包括应用事件、定时保存、历史与关闭的面板），使用虚拟时钟加速。普通战斗和迷宫分别回放 3,000 波，每波 10 次、每次 100 伤害，间隔虚拟 3 秒。公会试炼使用一个持续存活的 Boss，回放 30,000 次伤害，同时插入 300 波并行普通战斗，确认不会混入试炼。三种模式都由 WebSocket getter 入队，不直接调用统计方法。

| 模式                   | 10,000 次伤害后 JS heap | 20,000 次后 | 30,000 次后 |
| ---------------------- | ----------------------: | ----------: | ----------: |
| 普通挂机               |               3,678,984 |   3,727,480 |   3,730,808 |
| 迷宫                   |               3,774,556 |   3,783,440 |   3,789,292 |
| 公会试炼及并行普通战斗 |               3,818,752 |   3,878,340 |   3,880,860 |

每种模式累计伤害严格等于 3,000,000，完整图表始终最多 1,900 点、片段始终 1 个；DOM nodes 始终 45，监听器始终 59。活动缓存约 18.7 KB，后两个采样点只存在计数位数变化；历史仅在切换模式时增加归档。同一模式后两个采样点没有按消息数量同比例增长。普通战斗、迷宫、试炼名称与模式标记正确；试炼只保留公会玩家。虚拟时钟不等同于 25 小时真实后台运行。

夹具没有加载脚本管理器桥接、完整游戏 UI、其他脚本或网络请求；不能据此排除这些环境中的增长。刷新定时器在该夹具中暂停，消息驱动的实际 `persistActive` 路径仍正常执行；关闭面板的周期刷新行为另由已有集成测试验证。

### 其他被动路径复核

- 普通战斗每波替换血蓝、计数器、名字映射和持续伤害时间轴；持续伤害施法记录另按到期时间清理。公会试炼每层重建差值基线。命中与伤害来源按玩家／怪物种类／技能汇总，不保存每次攻击原始消息。
- 战斗 Buff 的单位状态用 WeakMap；待应用数组在同一次更新中清空，新波清空战斗 Map；没有战斗 DOM 时不继续追加待应用记录。倒计时最多挂一个任务。
- 活动 DPS 缓存覆盖同一个 key；战斗历史限制数量与总字节。历史共享字段的删除标记仍可能随不同战斗 ID 增长，属于跨场次存储的独立风险，本次没有证明它会在同一场持续挂机时逐条增长，也未贸然改变跨标签删除语义。
- 资产刷新合并待执行工作，同一天资产历史覆盖日期记录；初始化、每波战斗写入固定的脚本管理器 key，不能仅凭写入频繁认定 JS 对象无限保留。实际管理器桥接仍需玩家环境采样。
- 手动消息抓取默认关闭，不是本次无操作夹具的执行路径。

新增回归模拟定时器完全暂停时连续 4,000 条消息，并检查原始 payload、读取去重、顺序、处理数量及不依赖定时器；保留原有报错隔离、初始化状态、DPS、迷宫和公会归属测试。

本轮 `npm run build`、`npm run check`（测试单并发，593 项全部通过）、产物一致性校验和 `git diff --check` 均通过。本地测试命令已恢复原样，未提交本地配置。
